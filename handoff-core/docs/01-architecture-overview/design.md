# 模块一：核心架构演进与双层子母/双脑协同模型 (Architecture Overview)

本文档是 Chat-Codex 系统的顶层宏观架构设计规范，阐述了在 **Windows 纯原生环境** 下构建 **“浏览器子母版架构（Master-Worker Architecture）”** 与 **“Keeper-Broker 解耦协同体系”** 的工程标准与拓扑模型。

---

## 1. 传统架构演进痛点与淘汰动因

在实现高并发、高可用桌面大模型协同与深度检索任务时，业内常见的旧架构均存在不可克服的工程死穴：

| 架构模式 | 传统实现方式 | 致命工程缺陷与淘汰动因 |
|---|---|---|
| **GUI 独立多开方案** | 为每个任务拉起独立的完整 Chrome 窗口 | 单实例独占数百 MB 内存，10 路并发物理内存消耗高达 $4\sim 8\text{ GB}$；多窗口争抢前台焦点导致系统界面假死与崩溃。 |
| **外部发包模拟方案** | 用 Python / Node.js 携带 Cookie 直连后端 API | 缺失真实浏览器的 TLS 1.3 JA4 客户端指纹、HTTP/2 SETTINGS 帧序列，无法在外部执行动态难度 WebAssembly PoW 哈希碰撞与 Turnstile 挑战，**100% 触发 403 阻断**。 |
| **单沙盒排队锁方案** | 单个 Profile 并在单会话中串行排队 | 单会话存在前端输入锁（Stop 按钮水合期间不可输入），多任务串行排队延迟极高，单次网络中断导致全局死锁。 |
| **单体宿主强耦合方案** | IDE 直接持有 Chrome 调试句柄与进程树 | 终端会话关闭或 IDE 重启时，级联杀死正在执行长程推理的后台 Chrome 实例，导致未决任务丢失与会话损坏。 |

---

## 2. 现代全域多层解耦架构拓扑

系统确立了 **“L0 母本基座 + L1 物理实例 + L2 瞬态页签”** 与 **“Keeper 宿主 + Broker 调度”** 的全域多层运行架构：

```text
====================================================================================================
               Chat-Codex 全域多层架构拓扑 (双脑协同 + Keeper-Broker 解耦)
====================================================================================================

      +------------------------------------------------------------------------+
      |               本地工作区 (VS Code / Cursor / Antigravity 本地执行环境)      |
      |                                                                        |
      |   1. 提取关键符号、局部报错、Git 变更树                                  |
      |   2. 组装脱敏契约包 (Context Packet: 1~3K Tokens，6大固定段落)             |
      |   3. 确立本地决策主权: ChatGPT 仅作为推理顾问，执行权与决策权锁定在本地   |
      +-----------------------------------+------------------------------------+
                                          | JSON-RPC 2.0 / CLI 异步任务调用
                                          v
      +------------------------------------------------------------------------+
      |              任务协调中枢 (Broker: handoff-core Integration Engine)     |
      |                                                                        |
      |   * 职责: 任务状态机持久化、跨进程锁、重试退避、结果核对与索引构建        |
      |   * 生命周期: 可随时重启，不影响正在运行的 Chrome 实例                   |
      |   * 任务状态机: ACCEPTED -> DISPATCHING -> UNKNOWN -> EFFECT_VERIFIED  |
      +-----------------------------------+------------------------------------+
                                          | 租约校验与命令路由 (ownerEpoch)
                                          v
      +------------------------------------------------------------------------+
      |              常驻浏览器宿主 (Keeper: Resident Browser Host)             |
      |                                                                        |
      |   * 职责: 极简稳定，持有浏览器进程句柄与 Job Object，负责 CDP 命令分发  |
      |   * 故障隔离: 模型推理、文件扫描等重型逻辑彻底剥离，Keeper 崩溃率趋于 0 |
      +-----------------------------------+------------------------------------+
                                          | 原生 CDP (Chrome DevTools Protocol)
                                          v
      +------------------------------------------------------------------------+
      |          Chrome 双层沙盒架构 (Dual-Tier CDP Isolation Architecture)     |
      |                                                                        |
      |   [L0 母本沙盒: Port 9225] -> 人工登录保鲜，零自动化污染，纯内存凭据源    |
      |   [L1 工作沙盒: Port 9222/9223] -> sub-instance-1 / sub-instance-2     |
      |   [L2 瞬态页签: Ephemeral Tabs] -> PUT /json/new 开辟，完成即关释放内存  |
      +-----------------------------------+------------------------------------+
```

## 3. 核心解耦层次详解

### 3.1 Level 0: 凭据母本基座 (Master Seed Profile, Port 9225)
- **物理路径**：`C:\GPT-Chat-codex-handoff\master-seed-profile\`
- **核心职能**：唯一的免受自动化污染的人工登录基座。用户在屏幕前完成登录后，维持有效 Session（数月有效期）。
- **铁律约束**：**严禁任何自动化脚本直接以该 Profile 启动自动化测试或注入 Prompt**。该基座仅用于通过 CDP Browser Target 纯内存导出 Cookie。

### 3.2 Level 1: 物理工作实例解耦 (Worker Instances, Port 9222/9223)
- **物理路径**：`C:\code\Chat-Codex\sub-instance-1\`（Port 9222）、`sub-instance-2\`（Port 9223）
- **核心职能**：日常任务承载沙盒。启动时通过内存注入从 Master 派发的最新 Session Token。
- **治理原则**：视为“可复位的无状态易耗品”。受保护目录不可移动，但缓存与工作状态紊乱时可秒级刷新内存凭据重置。

### 3.3 Level 2: 会话页签子母解耦 (Ephemeral Tab Workers)
- **核心机制**：Worker 内部不采用单会话串行模式，而是通过 CDP HTTP 原语 `PUT /json/new?https://chatgpt.com/` 动态开辟全新隔离 Tab。
- **内存回收**：单个生成任务收敛（停止按钮消失且 Markdown 提取完成）后，**必须在 1 秒内调用 `/json/close/{targetId}` 显式销毁页签**，物理释放 Blink Renderer 进程与 V8 堆内存，单实例常态驻留内存压降至 **~84MB**。

## 4. 2026 前沿架构升级：Keeper - Broker 模式与不变量矩阵

针对长程推理过程中 IDE 重启、网络抖动导致的链路脆弱性，系统引入了业界最新的 **Keeper - Broker 双进程拓扑**，明确了六大系统不变量：

| 系统不变量 (Invariant) | 核心工程含义与防御机制 |
|---|---|
| **1. IDE 退出 $\neq$ 任务取消** | IDE 仅持有客户端通信连接，不持有决定 Chrome 存亡的最后一个 Job 或管道句柄；IDE 重启后通过任务 ID 重新 attach 既有任务。 |
| **2. Broker 重启 $\neq$ 浏览器重启** | 常驻宿主 Keeper 持有浏览器句柄与 CDP 连接；Broker 崩溃重启后自动重新连接 Keeper，不影响正在流式生成的 Web 页面。 |
| **3. 连接断开 $\neq$ 操作未执行** | CDP 连接异常断开时，正在发送的操作进入 `UNKNOWN` 状态；重连后先核对远端会话树，禁止直接盲目重放造成二次点击。 |
| **4. Handoff 唯一写入者原则** | 同一浏览器资源在任何时刻只能有唯一写入者；通过递增的 `ownerEpoch` 租约进行门禁断言，旧端的在途指令直接失效。 |
| **5. Worker 故障不波及宿主** | 单个代码执行 Worker 运行在专属的 Worker Job 中，超时或死循环触发硬杀时，不波及 Browser Job 与 Keeper。 |
| **6. 进程存活 $\neq$ 任务仍在推进** | 建立传输层（Ping/Pong）、浏览器层（Browser.getVersion）与任务层（DOM 增量与流式状态）三级独立监控，分别识别僵死。 |

## 5. 四类生命周期标识的分离

在系统内部，严格区分以下四类生命周期范围，杜绝混淆：

1. **`taskId`（业务任务域）**：唯一标识一次用户端发起的长程推理或调试任务，任务结束前保持不可变。
2. **`browserEpoch`（浏览器实例域）**：标识一次 Chrome 物理进程的生命周期，Chrome 进程重启时递增。
3. **`connectionEpoch`（传输通道域）**：标识一次 CDP 连接的建立，WebSocket 重连或端口重新发现时递增。
4. **`ownerEpoch`（写入权限租约域）**：标识当前控制权的授予代次，双脑 Handoff 或人工介入接管时严格递增。
